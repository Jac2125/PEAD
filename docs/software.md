## 0. 이 문서의 목적

분석 코드를 쓰기 전에 **무엇을 만들고, 무엇을 만들지 않으며, 완성을 어떻게 판정하는가**를 고정한다.

일반 소프트웨어 계획서와 다른 점이 하나 있다. 이 프로젝트에서 "버그"는 프로그램이 죽는 것이 아니라 **틀린 숫자를 조용히 내놓는 것**이다. 잘못된 이벤트 정렬이나 미래 정보 누출은 예외를 던지지 않는다. 그냥 그럴듯한 t값을 준다. 따라서 이 계획의 무게중심은 기능 구현이 아니라 **§6 검증 전략**에 있다.

## 1. 범위

### 1.1 목표

같은 기업이 S&P 500에 편입되기 전과 후로 PEAD의 크기가 달라지는가를 통계적으로 검정한다. 처치는 편입에 수반되는 애널리스트 커버리지·유동성·기관 보유의 증가이며, 가설은 정보 과소반응이 처치 후 약해진다는 것이다.

### 1.2 비목표 (명시적으로 하지 않는 것)

- 백테스트, 수익률 시뮬레이션, 거래비용 모형, 포트폴리오 구성
- 실시간 데이터 파이프라인, 스케줄러, 서빙 인프라
- 웹 UI, 대시보드
- PEAD의 존재 자체에 대한 재검증 (S&P 500 대형주 null 결과는 기확립으로 취급)

비목표를 적는 이유는 겸손이 아니라 방어다. "열 갈래 길"이 보이는 성향에 대한 구조적 대응이며, 여기 없는 것을 하고 싶어지면 이 문서를 고치는 커밋이 먼저 찍혀야 한다.

### 1.3 산출물

| 산출물 | 형태 |

| 사전등록 문서 | `docs/preregistration.md` |

## 2. 아키텍처 원칙

### P1. 단방향 데이터 흐름

```
raw  →  interim  →  results
(불변)   (파생)      (파생)
```

`raw`는 한 번 쓰면 수정하지 않는다. 하위 층은 언제든 삭제 후 재생성 가능해야 하고, 실제로 그렇게 되는지 주기적으로 확인한다.

### P2. 자유도의 단일 출처

윈도우 길이, SUE 임계값, 이상치 컷, 최소 관측일 수 등 연구자가 임의로 정할 수 있는 모든 값은 `config.yaml`에만 존재한다. 소스 코드에 숫자 리터럴이 있으면 그것은 버그로 간주한다.

이는 편의 기능이 아니라 **감사 추적 장치**다. 자유도를 만진 이력이 전부 git diff에 남는다. p-hacking에 대한 방어는 의지가 아니라 기록이다.

### P3. 순수 계산과 부수효과의 분리

네트워크 I/O를 하는 코드와 숫자를 계산하는 코드를 같은 함수에 두지 않는다. CAR 계산, 윈도우 정렬, SUE 산출은 전부 `DataFrame → DataFrame` 순수함수여야 하며, 그래야 §6의 합성 데이터 검증이 가능하다.

### P4. 단계 간 디스크 경계

각 단계는 산출물을 디스크에 떨구고 끝난다. 추론 방식을 바꿀 때 재수집이 발생하지 않게 하기 위함이며, 미뤄둔 세 가지 검증(층화표본·경계분석·클러스터 표준오차)을 나중에 싸게 붙이기 위한 구조이기도 하다.

```

  calendar.py      거래일 달력, 이벤트일 정렬, BMO/AMC 처리
  fetch/
    prices.py      가격 수집 → data/raw/prices/
    earnings.py    실적 발표일·EPS 수집
    index_events.py  편입·편출 이력 수집
  build/
    events.py      이벤트 테이블 조립, 자격 필터
    sue.py         서프라이즈 계산
  estimate/
    market_model.py  추정윈도우 OLS, 초과수익, CAR
  infer/

  report/
```

### 3.1 데이터 계약

각 층의 스키마를 여기서 고정한다. 스키마 변경은 이 문서 수정을 동반한다.

**`interim/events.parquet`**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `event_id` | str | `{ticker}_{announce_date}` |
| `ticker` | str | |
| `permanent_id` | str | 티커 변경에 불변인 식별자 (§11 Q2) |
| `announce_date` | date | 실적 발표일 |
| `announce_timing` | enum | `BMO` / `AMC` / `UNKNOWN` |
| `day0` | date | 초과수익 누적 시작 거래일 |
| `eps_actual` | float | |
| `eps_expected` | float | |
| `sue` | float | |
| `treatment` | enum | `PRE` / `POST` / `EXCLUDED` |
| `index_effective_date` | date | 편입·편출 발효일 |
| `months_to_event` | int | 편입일 기준 상대 시점 (음수=편입 전) |

`treatment`에 `EXCLUDED`를 둔 것이 핵심이다. 편입일 근처의 실적 이벤트는 인덱스 자금 흐름이 CAR을 오염시키므로, 배제 구간을 **데이터에 명시적으로 기록**하고 코드가 조용히 건너뛰지 않게 한다.

**`results/car.parquet`**

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `event_id` | str | |
| `spec` | enum | `market_model` / `market_adjusted` / `compromise` |
| `window` | str | 예: `(1,30)` |
| `car` | float | 단일 terminal 값 |
| `n_trading_days` | int | 실제 사용 거래일 수 |
| `est_alpha`, `est_beta` | float | 진단용 |

CAR이 **event당 한 행**이라는 것이 v1 설계 오류에 대한 스키마 수준의 방어다. 경로를 저장하지 않으면 경로를 t-test에 넣는 실수를 할 수 없다.

## 5. 요구사항

### 5.1 기능 요구사항

- FR1. 편입·편출 이력을 발효일과 함께 수집한다.
- FR2. 각 대상 기업의 편입 전후 N분기 실적 발표일과 EPS를 수집한다.
- FR3. 이벤트별 terminal CAR을 세 가지 벤치마크 spec으로 산출한다.
- FR4. 편입 전후 CAR 차이를 검정하되, 기업 수준 클러스터를 반영한다.
- FR5. 대조군을 포함한 이중차분 추정을 지원한다.

### 5.2 정확성 요구사항 (기능보다 우선)

- CR1. **미래 정보 불사용.** 추정윈도우는 이벤트윈도우보다 전부 앞선다. 갭을 둔다.
- CR2. **관측 단위 = 기업.** 한 기업의 여러 분기 CAR은 상관되어 있다. 유효 표본은 이벤트 수가 아니다.
- CR3. **날짜 클러스터링.** 같은 날 발표한 기업들의 CAR은 상관되어 있다.
- CR4. **구성종목 시점 정합.** 이벤트 시점의 구성종목을 쓴다. 현재 스냅샷은 survivorship bias를 만든다.
- CR5. **결측의 명시적 처리.** 데이터 없음을 조용히 dropna하지 않는다. 사유별로 태깅한다.

## 6. 검증 전략 ★

이 프로젝트의 중심이다. 통계 코드는 틀려도 정상 종료되므로, 일반적인 단위 테스트만으로는 부족하다. 세 층으로 방어한다.

### 6.1 불변식 테스트

계산 결과가 만족해야 하는 성질을 코드로 박아둔다.

- `est_window_end < event_window_start` — 모든 이벤트에서 참
- `n_trading_days == config.window_length` — 아니면 해당 이벤트 탈락
- `event_id` 유일성
- BMO/AMC에 따른 `day0` 정의가 일관
- `treatment` 태깅이 배제 구간과 모순 없음

### 6.2 합성 데이터 오라클 ★★

**정답을 아는 데이터를 만들어 파이프라인이 그 정답을 되찾는지 본다.** 실제 데이터에서는 참값을 모르므로, 이것이 파이프라인의 정확성을 확인할 수 있는 유일한 방법이다.

| 테스트 | 생성 | 기대 결과 |
|---|---|---|
| T1 귀무 | drift 없는 기하 브라운 운동 | p값이 균등분포, 기각률 ≈ 유의수준 |
| T2 회수 | 알려진 크기 d의 drift 주입 | 추정 CAAR이 d를 신뢰구간 안에서 회수 |
| T3 alpha anchoring | α≠0, 실제 drift 0 | market model CAAR은 선형 증가, 대칭 윈도우 CAR_diff는 0 |
| T4 클러스터 | 같은 날짜에 상관된 이벤트 | 단순 t는 과대기각, 클러스터 보정 후 정상 |
| T5 누출 | 이벤트 직후에만 신호 주입 | 추정윈도우 계수가 영향받지 않음 |

**T3가 특히 중요하다.** 지난 프로젝트에서 직접 유도한 결과 — 대칭 윈도우에서 Tα̂ 항이 대수적으로 소거된다 — 를 회귀 테스트로 고정한 것이다. 이 성질이 깨지면 즉시 알 수 있다.

**T1은 검정력 계산의 재료이기도 하다.** 실제 표본 크기와 실제 CAR 표준편차로 T1을 반복하면, 검출 가능한 최소효과크기가 나온다. 이 값이 이론적으로 기대되는 효과보다 크면 **연구를 시작하기 전에 접는다.**

### 6.3 외부 벤치마크 대조

전체 파이프라인을 문헌에 결과가 알려진 설정으로 한 번 돌린다. 부호와 대략적 크기가 문헌과 어긋나면 설계가 아니라 구현을 의심한다.

## 8. 프로세스 통제 (p-hacking 방어)

- G1. `docs/preregistration.md`가 분석 코드보다 **먼저** 커밋된다. 타임스탬프가 증거다.
- G2. 사전등록 이후 config 변경은 별도 커밋으로 사유를 남긴다.
- G3. 단계 03은 세 spec을 항상 함께 낸다. 사후 선택 불가.
- G4. 탐색적 분석은 `notebooks/exploratory/`에 격리하고, 결과 주장에 인용하지 않는다.
- G5. 반증 조건이 충족되면 문서에 기록한다. 조건을 고치지 않는다.

G5가 가장 지키기 어렵다. 이 문서에 적어두는 이유가 그것이다.

## 11. 열린 결정 사항

v1.0 확정 전에 답해야 할 것들이다. 답은 재민 님이 정한다.

- **Q1.** 편입 전후 각 몇 분기를 볼 것인가. 길면 검정력이 오르지만 RK2가 심해진다.
- **Q2.** 티커 변경에 불변인 식별자를 무엇으로 할 것인가. CIK인가, 수기 매핑인가.
- **Q3.** 대조군을 어떻게 구성할 것인가. 편입 후보였으나 편입되지 않은 기업인가, 규모 매칭인가.
